# agent-hub — техническая спецификация

Личный мульти-агентный ассистент в WhatsApp: ищет товары и поставщиков, собирает базу клиентов, готовит и шлёт рассылку (после аппрува), разбирает входящие, пишет и ревьюит код, мониторит цены. Управляется сообщениями в WhatsApp и веб-админкой.

---

## 1. Общая картина

```
   ТЫ (WhatsApp) ──┐                               ┌── БРАУЗЕР (/admin)
                   │                               │
                   ▼                               ▼
            ┌─────────────────────────────────────────────┐
            │            InstaPods (Linux-под)             │
            │  FastAPI-приложение (порт 8000, HTTPS)       │
            │                                              │
            │  /webhooks/greenapi  ◄── Green API (облако)  │
            │        │                                     │
            │        ▼                                     │
            │   ОРКЕСТРАТОР (LLM с инструментами)          │
            │        │ раздаёт задачи                      │
            │        ▼                                     │
            │  ┌─ Поиск товаров     ┌─ Рассылка            │
            │  ├─ Поиск клиентов    ├─ Входящие            │
            │  ├─ Код (ген+ревью)   ├─ Мониторинг цен      │
            │  └─ Память (выжимки)  └─ Реклама (заглушка)  │
            │        │                                     │
            │        ▼                                     │
            │  PostgreSQL (на том же поде)                 │
            │  APScheduler (рассылка / мониторинг по часам)│
            └─────────────────────────────────────────────┘
                   │                  │
                   ▼                  ▼
            OpenRouter (LLM)   Внешние API: Serper, 2GIS,
                               WB, Google Sheets, любые сайты
```

**Путь сообщения.** Ты пишешь ассистенту в WhatsApp → Green API дёргает `POST /webhooks/greenapi` → приложение проверяет токен вебхука и что номер твой → оркестратор получает текст + компактный контекст из памяти → решает: ответить словами или дёрнуть инструмент → долгие работы уходят в фон (`tasks`), мгновенные — выполняются сразу → ответ уходит тебе в WhatsApp через Green API. Фоном память извлекает факты и сжимает старую переписку.

## 2. Каскад моделей (экономия токенов)

Все LLM-вызовы идут через **OpenRouter** (один API-ключ на все модели). Модели разбиты на ярусы:

| Ярус | Дефолт | Кто использует | Зачем |
|---|---|---|---|
| `cheap` | `google/gemini-2.5-flash` | поиск товаров/клиентов, черновики рассылки, классификация входящих, генерация кода, парсер цен, вся память | ~85% вызовов, копеечная цена |
| `strong` | `anthropic/claude-sonnet-4.5` | редактор рассылки, код-ревьюер | мало вызовов, где важно качество |
| `orchestrator` | = `cheap` (можно поднять) | оркестратор | роутинг команд |

Приоритет выбора модели для конкретного агента:
**персональная модель агента (админка) → модель яруса (админка) → дефолт яруса (.env)**.

Защита от зацикливания: `UsageLimits(request_limit=...)` — оркестратор максимум 6 LLM-запросов на сообщение, поисковые агенты — 15 на задачу. Код-агент — максимум 3 итерации «генерация → ревью».

Экономия токенов: все модели создаются с `openrouter_cache_instructions="1h"` — системный промпт кэшируется OpenRouter'ом на стороне провайдера (Gemini/Anthropic) и не тарифицируется повторно на каждом шаге цикла.

**Fallback при ошибках провайдера.** Все вызовы агентов идут через `run_safe()`, которая перехватывает `ModelHTTPError` со статусами `{400, 429, 502, 503}`: 400 — модель не поддерживает формат запроса (JSON-schema) → немедленный fallback; 429 (rate limit) → `asyncio.sleep(5)`, затем fallback; 502/503 — временная недоступность → немедленный fallback. Запасной ярус задаётся полем `AgentSpec.fallback_tier` (дефолт `"strong"`), что позволяет настроить его индивидуально для каждого агента. Каждый fallback пишется в `error_log`; WhatsApp при этом ошибку не получает. После каждого успешного вызова (в т.ч. fallback) расход токенов записывается в `token_log` функцией `_log_tokens()`.

## 3. Память (4 уровня, минимум токенов в промпте)

| Уровень | Где живёт | Что хранит | Как попадает в промпт |
|---|---|---|---|
| Рабочее окно | `dialog_messages` | последние 8 сообщений | целиком (обрезка по 800 символов) |
| Rolling summary | `dialog_state` | выжимка старой переписки ≤120 слов | целиком |
| Факты | `memory_facts` | долгосрочное: чем занимаешься, предпочтения, инструкции | топ-20 |
| Архив | `memory_archive` | полные результаты всех задач | только по запросу — полнотекстовый поиск (`tsvector`, русская морфология) |

Обслуживание — фоном после каждого обмена (`memory.maintain()`): дешёвая модель достаёт новые факты (≤3 за раз, потолок 100) и, когда несжатых сообщений >30, обновляет выжимку. Под-агенты истории диалога **не видят** — получают только короткий бриф задачи. Это главный механизм экономии.

## 4. Агенты (11 штук, все настраиваются в админке)

| Имя в реестре | Ярус | Инструменты | Что делает |
|---|---|---|---|
| `orchestrator` | orchestrator | 17 инструментов (см. ниже) | принимает твои сообщения, раздаёт задачи |
| `product` | cheap | `search_web`, `wb_search`, `fetch_page` | сравнение цен, поставщики, новинки → Google-таблица + сводка |
| `lead` | cheap | `twogis_search`, `search_web`, `fetch_page` | компании с телефонами по нише/городу → база + таблица |
| `outreach_drafter` | cheap | — | пишет первое сообщение лиду |
| `outreach_reviewer` | strong | — | вычитывает черновик перед аппрувом |
| `inbox_classifier` | cheap | — | классифицирует ответы лидов (интерес/вопрос/отказ/спам) + предлагает ответ |
| `code_generator` | cheap | — | пишет код по заданию |
| `code_critic` | strong | — | ревьюит код, до 3 итераций исправлений |
| `price_extractor` | cheap | — | достаёт цену/наличие из текста страницы (не-WB сайты) |
| `memory_summarizer` | cheap | — | сжимает старую переписку |
| `fact_extractor` | cheap | — | извлекает долгосрочные факты |

**Инструменты оркестратора:** `start_product_search`, `watch_product`, `list_watched_products`, `unwatch_product`, `run_price_check_now`, `start_lead_search`, `lead_overview`, `prepare_outreach`, `list_pending_outreach`, `approve_outreach`, `reject_outreach`, `send_to_lead`, `start_code_task`, `start_ads_task` (заглушка), `get_tasks`, `search_memory`, `remember`.

**Очередь сообщений владельца.** `handle_owner_message` не обрабатывает сообщение сам, а кладёт его в `asyncio.Queue`. Единственный фоновый воркер (`_worker`, стартует в `lifespan`) разбирает очередь по одному, по порядку — сообщения не теряются и приём не блокируется на время ответа оркестратора. Если в очереди скопилось больше 3 сообщений, владельцу уходит уведомление «принял N, обрабатываю по очереди». Длинные работы всё равно уходят в фон через `tasks.spawn`, поэтому воркер занят лишь на короткий ответ оркестратора.

**Динамическая сборка.** Агенты не зашиты в код намертво: модуль регистрирует «спеку» (дефолтный промпт, ярус, инструменты, `fallback_tier`) в `app/agents_registry.py`, а перед каждым запуском агент собирается из спеки + конфига в БД (`agent_configs`): персональная модель, переопределённый промпт, выключенные инструменты, вкл/выкл агента. Изменил в админке → действует со следующего запроса, без рестарта.

## 5. Ключевые сценарии

**Поиск товаров** — «найди робот-пылесос до 20к»: оркестратор → `start_product_search` → фоновая задача → агент ищет через WB API + веб → структурированный отчёт (`ProductReport`) → Google-таблица (или CSV в `data/exports/`) → результат тебе в WhatsApp + в архив памяти.

**Клиенты и рассылка** (полный конвейер):
1. «найди 30 кофеен в Казани» → `lead` собирает компании с телефонами (2GIS + веб) → таблица `companies` + `leads` (статус `new`) → Google-таблица.
2. «подготовь рассылку: предлагаем поставки зерна» → для каждого нового лида: дешёвая модель пишет персональный черновик → сильная вычитывает → статус `pending_approval` → все черновики приходят тебе.
3. Аппрув («одобри все» / «одобри 12,13» / кнопки в админке) → статус `approved`.
4. Планировщик каждые 15 минут шлёт пачку: ≤2 за тик, ≤20/день, паузы 45–180 сек (рандом) — лимиты редактируются в админке на лету. Отправка с рассыльного номера (или с ассистента, если второй не настроен).
5. Лид ответил → `inbox_classifier` определяет категорию, обновляет статус лида, присылает тебе вердикт + готовый ответ. Отправка ответа — только по твоей команде («отправь лиду 5: ...»).

**Код** — «напиши скрипт...»: генератор пишет → критик ревьюит → до 3 циклов исправлений → файлы в `data/code/task_N/` + вердикт ревью тебе.

**Мониторинг цен** — «следи за ценой <ссылка>»: WB — через публичный API карточки, прочие сайты — скрейп + `price_extractor`. Каждые 6 часов проверка; изменение цены ≥1% или смена наличия → алерт в WhatsApp. История — в `price_history`.

## 6. База данных (PostgreSQL, 14 таблиц)

Схема применяется идемпотентно при каждом старте (`app/schema.sql`, всё `IF NOT EXISTS`).

| Таблица | Назначение |
|---|---|
| `dialog_messages` | вся переписка с тобой (рабочее окно памяти) |
| `dialog_state` | rolling summary (одна строка, id=1) |
| `memory_facts` | долгосрочные факты (`active` для мягкого удаления) |
| `memory_archive` | архив результатов; `tsvector`-индекс для полнотекстового поиска |
| `tasks` | фоновые задачи: `pending → running → done/error`, результат внутри |
| `companies` | найденные компании (телефон нормализован, дедупликация по нему) |
| `leads` | статус работы с компанией: `new → queued → contacted → interested/question/declined/spam` |
| `outreach_messages` | сообщения рассылки: `pending_approval → approved → sent/failed/rejected` |
| `lead_messages` | переписка с каждым лидом (in/out) |
| `watched_products` | мониторинг цен (url, последняя цена, наличие) |
| `price_history` | история всех замеров |
| `app_settings` | key-value настройки из админки (модели ярусов, лимиты рассылки) |
| `agent_configs` | конфиг каждого агента: модель, промпт, выключенные инструменты, enabled |
| `token_log` | расход токенов каждого вызова агента: `agent_name`, `input/output/total_tokens`; агрегат — `GET /api/admin/tokens` |

## 7. Веб-админка (`/admin`)

Одна страница (тёмная тема, без сборки фронта), вход: логин `admin`, пароль `ADMIN_PASSWORD` из `.env`. Пароль не задан → админка выключена. API под `/api/admin/*`, та же авторизация (HTTP Basic).

| Вкладка | Что можно |
|---|---|
| Обзор | счётчики задач/лидов/рассылки/памяти, статус планировщика; авто-обновление 10 сек |
| Агенты | глобальные модели ярусов; на агента: персональная модель, свой системный промпт, вкл/выкл инструментов, вкл/выкл агента, сброс к дефолту |
| Задачи | живой список с результатами (клик по строке), авто-обновление 5 сек |
| Память | факты (добавить/удалить), выжимка переписки, поиск по архиву, последние сообщения диалога |
| Лиды | вся база со статусами и контактами |
| Рассылка | черновики на аппруве (одобрить/отклонить/все), счётчики, история отправки, ручной запуск тика |
| Мониторинг | список товаров, убрать, «проверить все сейчас»; статистика токенов по агентам за 7 дней (входящие / исходящие / всего / по дням) |
| Инструменты | статус подключений: поиск, 2GIS, WB, Sheets, оба WhatsApp-инстанса, OpenRouter |
| Настройки | лимиты рассылки (на лету), системные параметры (.env — для справки) |

Все правки админки живут в Postgres и применяются со следующего запроса агента — рестарт не нужен (исключение: значения из `.env`, в т.ч. интервалы планировщика).

## 10. Безопасность

- Команды ассистенту принимаются **только с твоего номера** (`OWNER_PHONE`); чужие сообщения на номер ассистента игнорируются.
- Вебхук защищён токеном (`GREEN_API_WEBHOOK_TOKEN` — проверяется заголовок).
- Админка — HTTP Basic поверх HTTPS InstaPods; без `ADMIN_PASSWORD` отключена.
- Секреты (`.env`, `secrets/`) в git не попадают (`.gitignore`); деплой — git pull на поде, секреты правятся прямо там.
- Рассылка физически не может уйти без аппрува: статус `pending_approval` не обрабатывается отправщиком.
- Лимиты рассылки против бана WhatsApp: ≤20/день, паузы 45–180 сек, пачки по 2.

## 11. Как расширять

**Новый под-агент** (например, реклама): создать `app/subagents/ads.py` — Pydantic-модель результата, промпт, `register(AgentSpec(...))`, функция `run()`; в `orchestrator.py` добавить инструмент `start_ads_task` в список `tools` спеки; упомянуть в системном промпте. Всё — агент сразу виден в админке.

**Новый инструмент агенту**: async-функция с docstring (его видит LLM) → добавить в `tools=[...]` спеки агента.

**Поменять модель/промпт/лимиты**: админка, без кода и рестарта.

## 12. Деплой и эксплуатация

- Код: GitHub `emsaallax/agent-hub` → InstaPods тянет из репо. Обновление: push → redeploy на поде.
- Старт приложения: ретраи подключения к Postgres (30×2 сек), затем идемпотентное применение схемы — порядок запуска сервисов не важен.
- Планировщик — внутри процесса (APScheduler): рассылка каждые 15 мин, мониторинг каждые 6 ч. Ручной запуск: `POST /jobs/outreach/tick`, `POST /jobs/monitoring/tick` или кнопки в админке.
- Логи и health: `/health`, логи пода в InstaPods.

**Известные ограничения:**
- Один воркер uvicorn — это норма для персональной нагрузки; кэш настроек рассчитан на один процесс.
- WhatsApp-рассылка с нового номера — риск бана: лимиты не задирать, номер прогревать.
- WB периодически меняет версии публичных эндпоинтов — клиент перебирает известные URL, но может потребоваться правка.
- Голосовые сообщения пока не распознаются (только текст).
